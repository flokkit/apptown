# Flokkit v1.0.0-rc.5

The fifth candidate for Flokkit 1.0. It replaces RC4 as the candidate running in
production with the maintainers; the two-week run before 1.0 starts on it
(from 17 October 2026).
It is RC4 plus the operability work planned for the first release (checking
a deployment's settings before building it, seeing why a deployment is
failing, protecting disks, and saying what backups cover) and fixes for
defects the companies eval (`eval/companies`) found on RC4.

- **A deploy missing a setting is refused before anything is built.** If the
  app declares a required secret or setting that the target deployment has
  no value for, the deploy (and a landing's release) stops before the image
  build and names the deployment and the missing name, never its value.
  Before, the images were built and published first and the deploy failed
  afterwards.
- **Why a deployment is failing.** A deployment's card has a diagnostics
  line naming the failing part and what to try first. Its details show each
  part's and need's container as the Docker host reports it now: running,
  stopped or gone, last exit code, out-of-memory kill, restart count, health
  check, and when each was read. A host that does not answer shows
  **unknown**, never stopped. **Read log** shows a part's newest 200 lines
  (at most 64 KiB) once, to someone who may operate the deployment; the
  forge keeps no copy. App Platform and Portainer deployments say they do
  not report these.
- **Disks.** Containers the forge starts keep at most about 30 MiB of log
  each (rotated at 10 MiB, three kept). New releases, previews, recoveries
  and worker tasks are refused while the disk they would write to is below
  its floor (the larger of 1 GiB and a twentieth of the disk) or cannot be
  read; the refusal says what is free. Stopping, taking down and removing
  are never refused. Infrastructure and each target's page show each disk's
  free space and when it was read. Containers made before this keep their
  old logs until they are next made again.
- **What backups cover.** Each deployment's protection (card and
  `forge data`) lists what its copies cover and marks the rest **not
  assessed**, always including data kept outside the deployment, such as
  uploads in an S3 bucket.
- **A rehearsal never gets the real credential its profile replaces.** When
  a secret's `rehearsal` profile declares a `default` (even an empty one),
  a recovery rehearsal or restored copy gets that value, not the
  deployment's bound one. Before, a bound value won, so a rehearsal could be
  handed the production write key.
- **`forge check` runs the image scan.** The agent's check now also runs
  the landing's image scanners (Trivy by default) against the image the
  landing would scan, as feedback. Before, image findings first appeared at
  landing, after people had accepted the change.
- **Smaller fixes.** `forge new --pack` with a pack the forge does not offer
  is refused before the project is made (before, it left a project with no
  pack). Forge's own runtime files never come back in a worker step's
  result, whatever the project's ignore file says. A first release says
  plainly that it is the first.
- **Stock packs.** `java-spring` runs on `eclipse-temurin:21-jre-noble`,
  whose base image carries no unpatched extra binary for the image scan to
  find. `node-fullstack` installs workspace dependencies and drops
  development dependencies from the runtime image. `wordpress-bedrock`
  takes its address from the host it is reached on, so `WP_HOME` is no
  longer required.

The compatibility promises and experimental boundaries remain in
[What 1.0 promises](/docs/guides/compatibility). The one-time
identity conversion applied to the maintainers' pre-1.0 installations; a new
install starts at the 1.0 baseline. Deployment policy,
recovery and sizing statements in the RC3 notes are unchanged. This release
adds one database migration (152: limit events record the generation they
happened under); upgrading from RC4 applies it.

## HTTP API changes

Three routes added since `v1.0.0-rc.4`; none removed or changed. All are
experimental, and their bodies are not described in the API description:

- `GET /api/v1/projects/{slug}/deployments/{name}/diagnostics`: the
  settled generation's runtime facts part by part, its limit events and any
  crash-loop hold. Needs the deployment's read.
- `GET /api/v1/projects/{slug}/deployments/{name}/logs?part=<part>`: one
  part's recent log, read on request and sent with
  `Cache-Control: private, no-store`. Needs the grant to operate the
  deployment (reading it is not enough, since a log can hold secrets); the
  part is checked against the running generation.
- `GET /api/v1/infrastructure/disks`: this forge's data folder and its
  worker's state and Docker data folders, with free space, floor and when
  each was read. Needs instance `deployment:read`.

Request and response shapes gained optional fields:

- Project creation (`POST /api/v1/projects`) takes an optional `pack`; a
  pack the forge does not offer is refused before the project is made.
  `forge new --pack` sends it.
- A deployment's protection has `coverage`: `assessed` and `notAssessed`
  lists.
- A target's disk capacity has `refuses`, `floor`, `path` and `readAt`; a
  host's share has `diskRefuses`.

A worker refuses a new task on a full disk with the existing refusal shape
(HTTP 422); the worker protocol range is unchanged.
