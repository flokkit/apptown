# Flokkit v1.0.0-rc.4

The fourth candidate for Flokkit 1.0, and the first meant to run in production
with the maintainers for two weeks before 1.0 is tagged.
It fixes two defects found on RC3 and adds the work finished after RC3:

- **An abandoned run stops its running steps.** Before, abandoning a change
  ended its run but left a running step going until it finished or timed
  out (an agent step for up to 40 minutes), spending model tokens and
  holding the change's folder. A running step now watches its attempt and is
  cancelled when the run ends; its outcome is recorded as a lost attempt.
  Stopping the forge is not abandonment and leaves work to resume as before.
- **A need's emulator gets a data folder wherever it is started for a short
  time** (test and check steps, previews, the helper's sandbox, worker
  private services, `forge dev`). The S3 emulator refused to start without
  one, so apps that need object storage failed their tests. An emulator that
  exits now reports its exit code and last log lines.
- **The chat on a phone** keeps most of the screen for the conversation: the
  change's actions sit in one row and what the chat is about folds into one
  line.
- **WordPress** (`wordpress-bedrock` pack) with MariaDB backup, restore and
  copy verification.
- **Named need sizes**: a catalogue need may offer named sizes, chosen with
  `size` on a need in `app.yaml`.
- **`replicas`** in `app.yaml` declares a part's instance count. Only `1` is
  supported; other values are refused at validation.
- **Deployment progress**: deploy steps show their phases while they run and
  afterwards in the step log.
- **Docker inventory**: a target's inventory names each resource once, keeps
  provider IDs stable across renames, and keeps the time of the last
  successful reading when a reading fails.
- **A companies eval** (`eval/companies`): a runner that creates and
  changes a set of fictional companies' apps through the forge, with the
  stack of each app chosen to cover every server pack.

The compatibility promises and experimental boundaries remain in
[What 1.0 promises](https://github.com/flokkit/apptown/blob/main/stock/docs/guides/compatibility.md). The one-time
identity conversion applied to the maintainers' pre-1.0 installations; a new
install starts at the 1.0 baseline. Deployment policy,
recovery and sizing statements in the RC3 notes are unchanged.

## HTTP API changes

No route changes since `v1.0.0-rc.3`, and the served description
(`/api/v1/openapi.json`) is unchanged. Response shapes gained optional fields:

- A dependency kind (`GET /api/v1/dependencies`) has `sizes`: each named size
  with its `description`, `resources` and `command`.
- A part's resources have `size`, the named need size in effect.
- A service spec has `data`, the emulator's data path.
- A target's inventory lists one entry per resource where it listed each
  recorded claim before; the entry shape is unchanged.

The API remains experimental.

## Deprecations

None.
