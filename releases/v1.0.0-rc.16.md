# Flokkit AppTown v1.0.0-rc.16

RC16 is about keeping software up to date without a person doing it by
hand. The Janitor, now under one Maintenance menu, keeps projects on current
packs, opens dependency, base-image and security-fix updates, checks them,
lands the routine ones under choices a person saved (or AppTown's defaults),
and releases them to deployments that take Janitor releases. Scheduled scans
watch each project's code and the images its deployments run, and a
Statistics page shows what the Janitor shipped and why the rest did not.
Attention items can be sent by webhook or email. Fly.io and AWS ECS on Fargate
join the deployment targets (beta), images live in one hub registry per
installation, and pages work at phone width. It includes all changes since
RC15. Several changes are breaking, and **the Janitor starts on by default**;
read "Breaking changes" before upgrading. Take matching database and file
backups before upgrading, as described in the
[upgrade guide](https://github.com/flokkit/apptown/blob/main/stock/docs/guides/upgrading.md).

## Breaking changes

Before upgrading:

- **One container registry per installation.** An installation now has one
  container-registry connector, the hub, which holds every project's release
  images under a repository named from its host, a prefix and the project.
  Per-project registry attachment and GitLab per-project registry setup are
  removed. **Operator step, before upgrading:** if Integrations lists more
  than one container registry, or a GitLab per-project one, replace them with
  one connector whose credential reaches every project's repository.
  Otherwise migration 224 stops the upgrade without changing data, with "The
  hub needs one registry connector with a shared credential; replace
  connectors: …". The migration removes per-project registry attachments. By
  default the hub keeps 90 days and the newest 10 releases per project, plus
  every image a target, a kept backup or a pending release needs; targets
  keep the running release, the last three good ones, seven days of releases
  and any release a kept backup was taken with. When the hub confirms a
  release image is gone, AppTown rebuilds it from the release's recorded
  commit and labels it rebuilt. See
  [Images: where they live and how long they're kept](https://github.com/flokkit/apptown/blob/main/stock/docs/guides/images.md).
- **Upgrade AppTown and its workers together.** Workers now stream a task's
  result files instead of answering them inline, so a database dump on a
  worker is no longer limited to 64 MiB (a dump may now be up to 16 GiB).
  This worker serves worker protocol 4 only, and an AppTown and worker of
  different releases refuse each other with "install AppTown and its worker
  from the same release". **Operator step:** stop AppTown and its workers,
  upgrade both, then start them. A step whose results the previous worker
  captured but AppTown had not yet read fails as "result not kept"; run it
  again.

After upgrading:

- **The Janitor starts on by default.** On its first start, an installation
  that has never saved Janitor choices turns on routine (patch and minor)
  dependency updates, security fixes, base images, toolchain patches for
  security fixes and packs, shown as "Set by AppTown". From then on the
  Janitor opens changes on its schedules, lands those that meet every
  required check under these choices without a person, and keeps projects on
  the newest pack publications. Each deployment's **Janitor releases**
  setting (on the deployment's Settings tab) is **Automatically** by default,
  so landed Janitor updates also reach deployments that follow main;
  the other settings are "In a release window" and "When a person says".
  Saved choices, including all-off ones, are left alone. **Operator step,
  right after upgrading:** review Maintenance › Settings and change what you
  do not want (or `apptown janitor choices`, then `apptown janitor set
  --dependencies off --revision <current revision>` with no other flags to
  turn everything off); turn the Janitor off for one project in its Settings
  › General, and choose each deployment's Janitor releases setting.
- **Janitor approvals become one set of Janitor choices.** Migration 242
  converts saved standing approvals into one current record of choices
  (dependency level, security fixes, base images, toolchain patches, packs)
  and keeps the earlier records for attribution. Consent for an exact set of
  projects, land-only consent and consent for selected deployments are
  removed; each project's level (Same as everywhere, Off, Routine or
  Aggressive, migrations 237 and 243) and each deployment's release settings
  remain. Janitor work accepted under an old approval cannot land after the
  conversion; the next scheduled run starts it again. `apptown janitor
  list`, `preview`, `enable`, `disable` and the per-rule `history` and
  `assess`, and `apptown janitor publication …`, are removed; use `apptown
  janitor choices`, `set`, `history` and `assess --run RUN`.
- **Static sites name the image that serves them.** AppTown no longer ships
  its own Caddy image for static parts: `.apptown/app.yaml` must carry
  `staticServer: caddy:<version>-alpine@sha256:<digest>`. Release builds,
  previews and local container development refuse a static part without it;
  running deployments keep running, and new projects get the pin when they
  are created. The Janitor moves an existing pin but never adds one.
  **Operator step, once, before the first static build after upgrading:**
  for each project with a static part and no `staticServer:`, open a change
  adding `staticServer: <answer>`, where the answer is the first line of
  `apptown image newest caddy:2-alpine --scope line`, and let it land.
- **Health checks are HTTP or TCP.** A part's `healthcheck:` command and
  `health.liveness.exec` probes are refused when the contract is read, and
  an HTTP liveness probe needs a declared port. Every target restarts a
  part whose process exits. Liveness on a part that is not public, such as
  a worker, is honoured only on App Platform; a Docker host, Portainer and
  Fly refuse it before anything is released (Portainer and Fly refuse
  structured liveness on every part). **Action:** before an app's next
  release, remove its command health check; where the target supports
  liveness (a public part on a Docker host, or a part with a port on App
  Platform) you may instead give the part a port and declare `health: { liveness: { http:
  /livez } }`. See
  [Health](https://github.com/flokkit/apptown/blob/main/stock/docs/guides/contract-reference.md#health).
- **Python apps declare their tool.** The platform check that the contract
  matches the code now reads `requirements.txt`, and a Python app whose
  building part names no tools fails it with "add python to the tools of the
  part that builds it" (its Python checks used to read not applicable).
  **Action:** add `tools: [python]` to that part.
- **The workflow approval option `inAdvanceAdmitsNotApplicable` is
  removed.** A check that does not apply, with its reason, now counts as met
  everywhere. Migration 231 removes the option from stored workflow versions
  and rewrites older stock approval sentences to "every check passing or not
  applicable, none excused"; a workflow you author that still declares it is
  refused. A yes given in advance under an older landing sentence now waits
  for a person at that landing. **Action:** remove the option from your own
  workflow files.
- **Fix declarations lose their commands.** Dependency updates run as agent
  work judged by a model, not as declared commands. Migration 241 removes
  `list`, `run`, `runMajor`, `runFor` and `appliesTo` from stored guidance
  `fixes`, and pack data that still uses them is refused; a fix declares
  `{kind: update, ecosystem, files}`.
- **Pack recommendations are removed.** Projects are offered the newest pack
  publication. `apptown pack recommend` and its API and page action are
  removed, and migration 239 drops stored recommended versions and
  publication classifications.
- **Change titles are at most 100 characters.** Longer titles, including
  edits, are refused with "Title is the goal in a few words; put the
  instructions in the body." Existing titles are kept. Scripts that put
  instructions in the title must move them to the body.
- **Step containers run with `CI=true`, `NO_COLOR=1`, `TERM=dumb` and
  `FORCE_COLOR=0`** unless the step sets them, and recorded step output has
  terminal colour codes removed.
- **Release images are built without cache,** in a fresh Docker daemon, so
  builds can take longer. The stock security scan workflow can rebuild and
  release the same commit when a running image shows a newly fixable
  operating-system finding, on deployments that follow main and under their
  approval and window rules; leave `rebuild` out of your own security
  workflow if you do not want that.
- **Static parts that declare no memory get 64Mi** (was 512Mi) at their next
  release. On Fly the Machine stays at Fly's 256 MB minimum.
- **Bucket websites release only public deployments**, since anyone with
  the address can read their files.
- **`apptown data -p <slug> take-down <deployment>` follows a background
  operation** and no longer prints its own "taken down / deleted / kept"
  lines; every take-down runs in the background and pages show "taking
  down".
- **Disk warnings changed.** A disk warns at twice its refusal floor (at
  least 2 GiB, at most 40 GiB); the separate "Disk is N% full" item is gone,
  and missing or overdue readings say "disk space not known" with no
  figures.

Web addresses:

- **Maintenance replaces the Janitor menu item and the Conformance pages.**
  Maintenance has Needs you, Standards, Updates, Statistics and Settings.
  Old `/janitor`, `/janitor/settings` and Conformance addresses redirect.
  Project Janitor choices are in the project's Settings › General, and the
  project Overview no longer has Janitor or Releases sections. Setup's
  version page is now "AppTown updates". A change's chat address moved to the
  change page and redirects. Pack update approval moved to Maintenance;
  Packs links there.

HTTP API (see "HTTP API changes" for the full list):

- **The standing-approvals and routine-publication routes are removed**, as
  is `POST /api/v1/packs/{name}/recommended`. Change records replace
  `statusLabel` with `waitingOn`. Asking about a yes in advance
  (`GET …/adoption/in-advance`) must name its what-if (`fromWhatIf` or
  `selection`). Target capabilities rename `persistentVolumes` to
  `keepsDataDir` (migration 223). `/api/v1/guidance/blocks/{block}` takes
  the block's name instead of its id.

## New and improved

Maintenance and the Janitor:

- **Janitor choices** in Maintenance › Settings save as they change; each
  project can follow them, be off, or be Routine (patch and minor, weekly)
  or Aggressive (including majors, nightly). `apptown janitor run -p
  <project> [-queue <name>] [-again]` runs a project's queues now, and
  Run now is on each project.
- **Agent dependency updates.** An update runs as an agent session with
  Docker and the project's declared services, judged by AppTown's own tests,
  start-up and scans rather than the agent's account. Updates take stable
  releases only (a stable direct dependency may bring indirect
  pre-releases, and AppTown checks direct pre-releases with npm, uv, Go and
  Bundler's own lists). An update that changes nothing closes as "nothing
  to change". Base images follow the project's declared toolchain lines, and
  a digest pin of the same tag on its line is accepted. With Toolchain
  patches on, dependency updates and security fixes may move a declared
  toolchain and its image a patch within the declared minor (Go 1.27.0 to
  1.27.4, Node 24.22.2 to 24.22.3); minor and major moves of a declared
  toolchain need a change a person accepts that moves the declaration and
  the image together. Java, frontend-only and video-game packs declare
  dependency updates.
- **Security fixes** come from a daily scan; findings with no published fix
  or in the static file server are not targets.
- **Retries and Needs you.** AppTown's own failures retry up to three times,
  then offer Try again. Needs you explains what a proposed update does and
  offers Accept and Close. Janitor agent steps get 45 minutes.
- **Landing under standing choices.** A Janitor change accepted under the
  standing choices lands after catching up with main: the rule judges the
  new commit again, accepting it only when it is the accepted commit with
  main cleanly merged in and the routine classification still holds;
  otherwise the approval waits for a person with the reason. A routine
  landing also finishes after an optional bundle scan finding.
- **Statistics.** Maintenance › Statistics shows, for 7 or 30 days, runs by
  kind (shipped, nothing to change, waiting on a person, failed, closed,
  running), why work did not ship with examples, time to patch per
  deployment part, and the same per project.
- **Scans on a schedule.** Each project's code and the image each deployment
  runs are scanned on a schedule (the platform pack's new version adds a
  daily scan; adoption stays explicit). A missing, unfinished or older than
  three days scan reads as not known, never clean. Landing scans are reused
  for exactly the software released. Unassessable scans retry within an
  hour.
- **Guide:** [Who keeps what up to date](https://github.com/flokkit/apptown/blob/main/stock/docs/guides/who-keeps-what-updated.md).

Deployments and targets:

- **Fly.io Machines (beta)**, turned on in Setup → Features: each deployment
  is its own Fly app, with data folders on volumes, container Postgres,
  backups and restore, a final backup before take-down, Restart, and each
  part's state, CPU, memory and out-of-memory kills. Migration 222 gives
  existing Fly targets these abilities.
- **AWS ECS on Fargate (beta)** for one public Linux app with an optional
  dedicated RDS PostgreSQL database inside an AWS estate you manage, with
  CloudFormation and Terraform samples. The installation's role needs
  `ecr:BatchDeleteImage` on its repository prefix for image cleanup.
- **One setup guide per target kind**, linked from the product, and a
  Deployment targets section in the docs.
- **Audience and data** can be changed on a deployment's Settings tab, with
  a preview; New deployment and Create project ask for the target first and
  offer only its allowed values.
- **Portainer hosts** show the same capacity as Docker hosts, and a release
  is refused when Docker's data disk is below its floor or unreadable.
- **Releases.** All releases shows one line per release with what it
  brought, and a release's page lists its changes. Change and chat headers
  name the branch and the deployments following it, and each release
  appears on the change after landing.

Changes, chats and checks:

- **Landing brings main in itself** when it merges cleanly; on a conflict
  the change page names the files and offers Resolve in chat. Queued
  accepted work starts landing when the previous landing ends.
- **Send back with a note** on every approval; the note shows in the chat
  and in `apptown show` and `wait`. Decisions sit at the top of Overview.
- **Change progress** shows stage and step bars, running checks show elapsed
  time, and a required check that timed out offers Try again.
- **Chats.** The Conversation tab holds the live chat, earlier chats appear
  inline with "chat restarted" dividers, and on desktop an HTTPS preview can
  sit beside it, including apps that refuse framing. The chat terminal is
  read-only until Take control, and a stop reads as the person's. The chat
  helper retries a dropped model stream.
- **`apptown dev up`** gives the app `APPTOWN_APP_URL` and `APPTOWN_ORIGINS`
  and prints the last 50 log lines when it fails. `apptown land` inside a
  chat lands that chat's change. Frontend starters write a JUnit report so
  landing records test counts.

Notifications and pages:

- **Notifications** by webhook (JSON, Slack, Discord, Teams, ntfy) and SMTP
  email: warnings promptly, the rest in a daily digest, and a notice when a
  problem clears, set up on the Notifications page with test sends and
  delivery history.
- **Phone width.** A back link instead of the breadcrumb, rows that stack,
  menus and help as dialogs, a Decide bar on changes, and whole names;
  raw ids show only with Techno Goggles on.
- **Faster pages.** Attention, Maintenance, Projects and deployment pages read
  in batches, and after an act AppTown checks only the deployment that
  changed. The project page has Change beside Open app, and project setup
  ends with "Where it runs".

Fixes:

- Pages no longer contradict themselves about what is serving, counts,
  durations and unknowns; one deployment's start, stop or restart no longer
  makes its neighbours unknown (migration 221), and app status stays steady
  while a Docker host is busy or an app is deploying.
- One record of what each deployment serves (migrations 226, 227):
  deployments released by the old ship workflow no longer say "No serving
  release recorded", and failed releases no longer leave "replacement in
  progress".
- An in-place restore keeps every writer stopped until it ends; a lost
  container is repaired by its host's reader; a Fly or AWS deploy
  interrupted before it changed anything ends failed, not uncertain.
- Bucket sites no longer show false unknowns or Start/Stop controls, and a
  release no longer leaves browsers on old assets.
- Removing images by hand on a Docker host no longer leaves a failed target
  reading.
- Diff rubrics judge the change's own diff at landing, so pack adoption
  landings no longer error.
- Database deadlocks that lost workflow notices, failed approvals, or
  stalled a checkout while a chat opened are fixed.
- A change held on a failed scan step no longer crashes the change page.
- A restored AppTown that refuses to start names the failing step.
- The agent image adds `ps`, `pgrep` and `pkill`.
- Maintenance › Statistics table headings wrap at large text instead of
  pushing the page sideways.

## Declaration changes

- `.apptown/app.yaml`: new `staticServer`; `healthcheck` and
  `health.liveness.exec` are refused (see Breaking changes).
- Workflows add `metadata.title`; `on.schedule` adds `standing`, `queue` and
  `aggressiveCron`; a new `on.publication` trigger (`queue`, `standing`);
  approvals add `standing: {class, means}`; new step kinds `rebuild`
  (`whenFailed`), `fix` and `routine`; `agent/pi` adds `repairRounds`,
  `scan` adds `baseline: none` and `on: bundle`, and `workflow/call` adds
  `whenFailed` and `findings`. `approval.inAdvanceAdmitsNotApplicable` is
  removed.
- Guidance blocks add `fixes` (`kind`, `ecosystem`, `files`).
- Scanners add `kind: prerelease`. The dependency catalogue adds a provider
  `setup` field.
- New stock workflows: `janitor-scan`, `janitor-update`, `janitor-fix`,
  `janitor-adopt` and `rebuild`. New pack versions carry them; adoption is
  a pack update like any other.

## HTTP API changes

These changes are relative to RC15. The HTTP API remains experimental. The
[OpenAPI description](https://github.com/flokkit/apptown/blob/main/stock/docs/api/openapi.json)
contains the available route definitions.

- Added: `GET /api/v1/janitor`, `GET /api/v1/janitor/statistics?days=7|30`,
  `GET /api/v1/janitor/history`, `GET` and `PUT /api/v1/janitor/choices`
  (body `{"choices", "expectedRevision"}`),
  `GET /api/v1/janitor/choices/history` and `POST /api/v1/janitor/assess`
  (body `{"run"}`).
- Added: `GET /api/v1/projects/{slug}/scans`,
  `GET /api/v1/projects/{slug}/janitor/attempts`,
  `POST /api/v1/projects/{slug}/janitor/run` (`{"queue", "again",
  "changeId"}`), `POST /api/v1/projects/{slug}/janitor/{queue}/skip`,
  `POST /api/v1/projects/{slug}/janitor/settings` and
  `POST /api/v1/projects/{slug}/schedules/{workflow}/run`.
- Added: `GET` and `PUT /api/v1/projects/{slug}/deployments/{name}/classification`
  and `PUT /api/v1/projects/{slug}/deployments/{name}/routine-updates`.
- Added: `GET /api/v1/image-lines?ref=…&scope=…`,
  `GET /api/v1/notifications` and
  `POST /api/v1/notifications/channels/{name}/test`.
- Removed: `POST /api/v1/packs/{name}/recommended`; every
  `/api/v1/standing-approvals` route (list, create, preview, assess,
  disable, history); every `/api/v1/routine-publications` route (create,
  preview, revoke, history).
- Changed: `/api/v1/guidance/blocks/{id}` is `/api/v1/guidance/blocks/{block}`,
  addressed by name. `GET /api/v1/project-creation-targets` takes `audience`
  and `data`. `GET /api/v1/projects/{slug}/adoption/in-advance` requires
  `fromWhatIf` or `selection`. A change title over 100 characters is
  refused with 400.
- Changes: `Change` and `ChangeSummary` add `automatedOrigin` and `janitor`;
  the change page adds `goesTo` (`branch`, `deployments`) and `returnedBy`
  and drops `statusLabel`; change history and activity run rows drop
  `statusLabel`; the main-conflict record drops `step`; `ChangeCommit.when`
  may be `""`; a change's releases add `url`, `commitSha`, `stage`,
  `lastStage`, `failedStage`, `stageElapsedMs`, `hostOnly` and
  `progressUncertain`; `waitingOn` adds `queue`.
- Runs add `rebuildFrom`, `rebuildReleaseId` and `sourceCommit`; steps add
  `attempt`, `observation` and `progress`.
- Deployments add `routineUpdates` (`mode`, `days`, `from`, `to`, `zone`)
  and `routineUpdatesRevision`; deployment views also add `backups` and
  `runtimeActions` and drop `promotionBlocked`.
- Releases add `approvalRoleTitle`, `rebuiltFrom` and `rebuiltCommit`;
  release detail adds `replacedBy` and its changes add `number`; release
  decisions add `waitReason`; release bundles add `commit` and
  `rebuiltFrom`; release request metadata adds `routine`.
- Target capabilities replace `persistentVolumes` with `keepsDataDir`; kinds
  add `guide`; offered targets add `reason`; creation targets add `label`,
  `audiences`, `data` and `attributeFix`; project drafts add `audience` and
  `data`.
- The executor adds `hostTarget`; Attention coverage adds `conditions`,
  `notKnown` and `withheld`; ADR records add `statusHelp`.
- Standing assessment takes `run` (was `runId`) and adds `choices` and
  `level`, dropping `questionDigest`; standing revisions add `at` and
  `choices` and drop `changedAt`, `changedBy`, `enabledAt`, `question` and
  `reason`; standing inspection drops `advisories` and `images`; standing
  validation drops `node`, `npm` and `platform`; routine targets drop
  `classifications`. The project settings API no longer accepts or returns
  a Janitor `reason`.
- New values: display status `waiting for approval`; progress `not deployed`
  and `taking down`; backup `removed`.
- In the OpenAPI description, `AddsLine` is renamed `addsLine`, `Decider`
  `decider`, and `ReleaseChange` `ReleaseChangeTitle`; the standing-approval
  and routine-publication schemas are removed, and Janitor, scan, queue,
  finding and classification schemas are added.

## Deprecations

None.
