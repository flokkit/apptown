The first release candidate of Flokkit 1.0. What 1.0 promises, and what it
leaves experimental, is in [What 1.0 promises](/docs/guides/compatibility):
the formats you write, the command line's core loop and its `--json`, the MCP
tools, record identities and links, which versions work together, and your
data across upgrades. Install: Running a forge, Install.

The identity conversion to 1.0 was run once by hand on the maintainers'
pre-1.0 installations; a new install starts at the 1.0 baseline.
Links made
before 1.0 to a change (with its run and step), an ADR or a guidance block
move to the record's id.

Deployments now declare resources and profiles, record operator overrides, and
show observed memory and host capacity. Fresh container deployments use an
explicit declaration or override first, then the adopted pack, dependency
catalogue or Forge memory default. Rebuilding a recorded generation preserves
its applied limits. Provider-managed sizes remain separate.

The deployment policy API names today's behavior `compatible-update`.
`protected-maintenance` is reserved and returns “not implemented” before any
deployment effect. Automatic recovery is not implemented in this candidate.

## HTTP API changes

This is the first release: every route is described, marked experimental, in
the OpenAPI document a forge serves at `/api/v1/openapi.json`. Later
releases name each change here. The deployment read surfaces expose
`deploymentPolicy`; config accepts `compatible-update` or the reserved
`protected-maintenance`, with unavailable policy requests refused before effects.
The resource/profile override and target-capacity routes are listed in that
experimental API description; the resource and deployment guides describe
their behavior. Their request and success-body schemas remain unmodeled.
