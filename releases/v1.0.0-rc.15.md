# Flokkit AppTown v1.0.0-rc.15

RC15 is about deployments as things you manage. Landing now ends when the
merged code builds; each deployment then takes releases on its own terms:
following main, promoted from another deployment, or by hand. A deployment
can require a person's approval before it takes a release, can be rolled back
together with its data, and has visible Start, Stop and Restart controls,
live progress through named stages and one status word everywhere. Backing up
and restoring are done from the deployment's own menu. An administrator can
turn optional areas on and off in Setup → Features. Chats accept files,
projects can keep reviewed notes, and AppTown has a text size setting. It
includes all changes since RC14. Several changes are breaking; read "Breaking
changes" before upgrading. Take matching database and file backups before
upgrading, as described in the
[upgrade guide](https://github.com/flokkit/apptown/blob/main/stock/docs/guides/upgrading.md),
and follow
[Upgrading landing and deployment](https://github.com/flokkit/apptown/blob/main/design/operations/deploy-model-upgrade.md).

## Breaking changes

Landing and deployments:

- **Landing no longer deploys.** Landing finishes once the merged tree
  builds: a runtime project records a bundle, a project without a runtime
  records a clean-tree build, and neither starts a deployment or runs init
  steps against deployment data. Each deployment that follows main then
  requests that landing's bundle as a release; a refused or failed release
  leaves the change landed. The workflow `deploy` step and the stock `ship`
  workflow are removed. **Before upgrading, let in-flight landings finish:**
  the new build does not run the removed step. On upgrade, migration 215
  removes the retired workflow versions and the selections pinned to them,
  and a landing selection of `ship` returns to `land`. **If a workflow you
  authored still uses `deploy`, or calls a workflow that does, the upgrade
  stops without changing data** and names the workflows to edit (use
  `build` and repair their calls) or delete before upgrading again.
  Historical runs keep their recorded definitions.
- **Follows main must be confirmed by a person.** Migration 211 sets each
  project's `main` deployment (or `prod` where there is no `main`), and any
  deployment fed by landing, to follow main; promotion and schedule feeds
  become promotions from the follows-main deployment when there is one, and
  manual otherwise. The migration records no one as having chosen these
  settings, so **automatic releases fail with "follows main is not confirmed
  for this deployment" until a person confirms them**; landings still
  finish. **Operator step:** after upgrading, sign in as a person with
  deployment permission and run `apptown deployment confirm-feed --all`
  (protected deployments also need protected-release permission). One
  setting can be confirmed with `apptown deployment confirm-feed <project>
  <deployment>` or by saving **Follows main** in the deployment's Release
  feed setting, even unchanged. Agent credentials cannot confirm. Confirming
  does not replay a release that already failed.
- **`apptown retry --accept-uncopied-data` is removed.** Accepting that
  AppTown cannot copy a deployment's data belongs to a release: use
  `apptown release --accept-uncopied-data`. Automatic releases always stop
  when the pre-deploy copy fails.
- **New projects get a `main` deployment.** Create project now creates
  `main`, following main, on the chosen target (the default target unless
  another is picked under "Where it runs"), so the first landed change runs
  at the app's address. Choose **Nowhere yet**, or `apptown new --target
  none`, for no deployment. No deployment is made without a default target
  or deploy authority, and one made with an agent credential stays
  unconfirmed until a person confirms it.
- **The Backups page lists copies and has no actions.** Back up now,
  Restore from this copy, the restore-into box and Start a new deployment
  from a copy are gone from its rows; a row opens its deployment. **Back up
  now and Restore from a backup… are on the deployment's ⋯ menu** (Docker
  hosts and Portainer). Restore from a backup… lists the deployment's own
  copies and the final copies kept from the project's taken-down
  deployments; to restore a taken-down deployment's data into another
  deployment, open that deployment and choose Restore from a backup…. A new
  deployment starts from a copy in the New deployment form. A managed
  database's copy is never restored over a deployment.

Docker hosts:

- **Docker Engine 25 or newer (Docker Desktop 4.27 or newer) is required.**
  A deployment's services (postgres, mariadb and s3) are given a health
  check start interval (`--health-start-interval`), which needs Docker 25.
- **Service health checks run every 3 seconds while a service starts, then
  every 30 seconds,** with 3 retries; they ran every 3 seconds for the
  service's whole life. **A standing service created with the older timing
  is recreated on its existing storage at its deployment's next deploy,**
  so that database or store restarts once. The compose export uses the
  same timing.
- **Whole-host CPU and memory readings need cgroup v2.** Target CPU and
  memory strips now show the machine's own use, read by the same standing
  container that reads disk. On cgroup v1, or when the counters cannot be
  read, those readings are unknown with a reason. cgroup v2 is the default
  on current Linux distributions and Docker Desktop.

Features:

- **Optional areas can be switched off, and new installations start with
  beta areas off.** Setup → Features and `apptown features` list each area
  as always on, on by default or beta. An area that is off disappears from
  navigation, and its requests through the API, CLI and MCP are refused with
  a message naming the area. Always on: projects, changes, landing,
  releases, deployments, people, record, setup, ways of working, chats,
  usage, worker, previews, models and complaints. On by default:
  conformance, deployment backups, AppTown's own backups and update checks.
  Beta, off by default: evals, pack upgrades (what-ifs), restore rehearsals,
  the conformance estate view, App Platform, Portainer and bucket-site
  targets, **MCP for outside agents** and project memory. On upgrade,
  migration 218 turns on each beta area that the install already uses
  (stored evals, what-ifs or rehearsals, attached targets of that kind, MCP
  clients, consents or activity), and keeps project memory and the estate
  view on when any project exists. **Operator step:** after upgrading, check
  Setup → Features, and turn on MCP before outside coding agents connect to
  a new installation.

Chats:

- **The chat upload API takes multipart form data.** `POST
  /api/v1/console/{sid}/upload` takes the file's bytes in a multipart `file`
  field instead of a JSON data URL. **Upgrade AppTown and its worker
  together:** files now reach worker chats one at a time over a new
  transfer.

Changes and records:

- **Shortfalls in a change's end-of-change assessment must quote the
  person's words.** Migration 209 sets existing "partly" and "no"
  assessments, which have no quote, to unknown.

Web addresses:

- **Several pages moved, without redirects.** The Deployments group has
  four pages: Releases, Deployments, Targets and Backups; Targets holds each
  target's inventory, settings, offers and check. A project's Deployments
  page holds New deployment and its release preference, and Settings has no
  Deployments page. Decisions moved to the project's Memory › Decisions.
  People has separate Accounts, Groups, Roles, Sign-in, and Agents and
  tokens pages, replacing its query-tab addresses. Personal access tokens
  and connected coding agents are on Account. Background jobs are at
  `/jobs`. The branch import form and Janitor pages are removed from the web;
  their CLI and API remain. Update bookmarks.

HTTP API and CLI:

- **Target capabilities drop `previews`** (migration 217 removes the unused
  setting).
- **Deployment progress has a `backing-up` stage** before building, and a
  change's waiting-on `tone` can be `busy` (a change open in its chat).
  Clients that list these values must accept the new ones.

## New and improved

Deployments and releases:

- **Promotion between deployments.** A deployment can follow main, take
  promotions from another deployment in the same project, or release by
  hand (`apptown deployment set-feed <project> <deployment>
  main|manual|promotion [--from <deployment>]`). Promote names the release
  it sends and sends exactly the source's last settled bundle; it is
  refused when the source has since moved on or is seen stopped. A
  promotion source cannot be taken down while other deployments take
  promotions from it.
- **Release approval.** A deployment can require approval from a project
  role, such as the new Release manager role. A waiting release is approved
  by another eligible person, who accepts "I accept release N running on
  `<deployment>`"; the release records that sentence, who approved and how.
  Agent tokens cannot approve, and a newer request supersedes a waiting one.
  Approve and Cancel are on the deployment page and in `apptown release
  approve|cancel <project> <release-number>`; Home and Attention point
  eligible approvers there. Taking a deployment down cancels its waiting
  releases.
- **Choosing a release and rolling back with data.** Deployment history
  offers Deploy this again and Deploy a release…, listing each release's
  build date, new changes and where it runs or ran
  (`apptown release <project> <deployment> --release N`). Changing code
  keeps current data, and the confirmation says so. Roll back to before
  release N (`apptown rollback <project> <deployment> --before N`) restores
  that release's pre-deploy backup, after a safety copy, and runs the
  release that was running when the backup was taken. If it fails before
  the app starts, the restored data is kept and the app stays stopped.
- **Start, Stop and Restart.** Deployment pages show them beside the status,
  with who stopped the app and when (`apptown deployment start|stop|restart
  <project> <deployment>`). Stopping keeps data, address, secrets and
  settings; new releases can arrive while stopped without starting the app.
  Restart reuses the current release without a rebuild or backup. App
  Platform supports Restart only, and bucket websites none.
- **Interrupted releases finish.** At start-up AppTown checks a deployment
  whose release was interrupted, records it finished when that version is
  running, or retries it once when the provider confirms it was not
  applied. App Platform deployments carry enough in their spec for a lost
  response to be found without applying twice. A failed release offers Try
  again.
- **Live deploy progress on the deployment page.** Each release records its
  stages (preparing, backing up, building, starting, checking, live) and
  when each began; the page draws a house being built at the pace of the
  previous build, shows elapsed time, lights the failed stage on failure and
  says "It's live!" with the app's address on success. A change's Release
  row links to its deployment, and accepting a change opens it. Results show
  the backup taken before the release; release pages link to it, and the
  newest three pre-release backups are kept apart from the ordinary count.
- **One deployment status everywhere.** Projects, Deployments, Home, target
  pages and the CLI show the same status word, reason and check time; its
  details open on hover or tap. A running front door no longer hides a
  failed service. Right after a release the status reads "release N live —
  first check pending" until the next reading. Bucket websites show working
  when they answer.
- **Deployment pages** have Status, History and Settings tabs, list their
  containers with CPU and memory use, and show a Host line: whether the host
  takes new deploys, its memory against what the apps request, and a link to
  the host.

Hosts and capacity:

- **One reading per Docker host.** Each sweep inspects every container on a
  host in one Docker command, so a busy host no longer leaves its last apps
  unknown. A timeout says "the host reading timed out" and keeps the last
  reading visible as old. Capacity readings collect all their counters in
  one command and time out after 60 seconds.
- **Targets and Executor.** Target pages lead with status, capacity,
  deployments and resource counts, with resources, capacity and history on
  their own pages. Executor shows the worker's address, version (marking a
  different one), running work, previews and disks.
- **Disk use.** Usage shows workspace, database, local backup, Docker
  volume, image and build cache sizes and each filesystem's used and total
  space. Attention warns when a disk is more than 80% full. Finished
  evaluations remove their build caches, and workspace cleanup keeps saved
  conversations and session transcripts.

Changes and checks:

- **Declared tests run before a change is handed back.** Stock workflows
  run landing's tests step on the agent's committed work before preview,
  review and acceptance, and failures go back to the agent for up to three
  automatic rounds. Each test result records the commit's tree, the test
  declarations, the AppTown version, each command's image digest and the
  tool versions it used.
- **Standards check progress.** The check reports each check's position,
  name, verdict and time as it runs, on the change page, in landing progress
  and in `apptown wait`.
- **Conformance updates when a fix lands.** A landing's check results are
  saved at once, a repaired finding moves to Fixed with its change and
  commit, and each verdict shows its commit, date and source. Fleet reviews
  open as dated snapshots.
- **Chat changes summarise the request.** When chat work is ready for
  review, a short summary and title are written from the person's messages
  and shown as "You asked", with the approval brief, destination and
  approver. Shortfalls show the words they are based on.
- **A refused publication is recovered once.** When a resumed agent amends a
  commit already on the change branch, the refusal goes back to the agent
  for one automatic round to rebuild its work on top of the branch; a second
  refusal waits for a person.
- **Agent-judged checks** have a 250,000-token limit (was 400,000), set from
  measured use; the time limit stays 3 minutes.

Chats and projects:

- **Files in chats.** Attach, drop or paste any file up to 25 MB, ten per
  message. The agent is told who attached each file and where it is; files
  enter the change only as ordinary edits. Files are not scanned.
- **Write while the chat starts.** The composer is ready on first paint;
  words sent early are delivered once the helper is ready.
- **Project notes.** A project can keep reviewed facts and preferences in
  `PROJECT-NOTES.md`, shown under Memory › Notes; adding or removing a note
  opens a change. Guidance can declare repository files that agents and
  chats receive from the change's starting commit. AI-judged verdicts that
  rest only on `PROJECT-NOTES.md` or `AGENTS.md` become cannot-assess. The
  platform pack's new version carries the convention and a format check;
  adoption stays explicit.
- **Preview secrets for agents.** A preview secret binding can be made
  visible to agents. An Infisical key that a non-preview binding uses cannot
  be given to agents, and a running chat is recreated when its secrets
  change.
- **Settings › Models** shows the project's model profile and the model for
  each task.
- **Django test counts.** The Django guidance and starter write a JUnit
  report so landing records passed, failed and skipped counts. Adoption of
  the new pack version stays explicit.

Pages:

- **Text size.** The account menu offers Small, Medium (the default, 16px
  body text) and Large.
- **Project pages** have Overview, Changes, Deployments, Security, Settings
  and Memory, a ? help popover with a guide link on each title, and one main
  heading. Lists open by clicking the row; long records and dependent
  projects have their own pages; the breadcrumb comes from the page's
  address.
- **Clearer words and controls.** "Create project" replaces "New project".
  Switches share one control. In-page forms replace browser dialogs for
  finding confirmation, risk acceptance, remediation and eval deletion.
  Home's status strip labels each count and leaves out conditions AppTown
  could not read. App addresses show without `https://`, and Open the app
  opens a new tab.
- **Accounts** show "never signed in" until a person signs in or acts;
  changing group membership or grants no longer updates their last-seen
  time.

Fixes:

- The policy library loads after upgrading an install that stored the
  retired `ship` workflow.
- "Write this project's notes" starts instead of failing on an unfilled
  placeholder.
- Backups and deployment history links open the right pages.
- `github.com/klauspost/compress` is upgraded to v1.20.2 for advisory
  GO-2026-6865, a crash reachable when AppTown collects a worker's results.

## Declaration changes

The workflow `deploy` step kind and the stock `ship` workflow are removed
(see Breaking changes). Guidance may declare repository context with a
leading `<!-- context: [{"path": ..., "maxBytes": ...}] -->` comment, and
guidance check declarations may add `evidenceUse: wording`. No other
application-contract, workflow, check or pack declaration fields are added
or removed.

## HTTP API changes

These changes are relative to RC14. The HTTP API remains experimental. The
[OpenAPI description](https://github.com/flokkit/apptown/blob/main/stock/docs/api/openapi.json)
contains the available route definitions.

- Added: `GET /api/v1/features` and `PUT /api/v1/features/{area}` (body
  `{"expected", "enabled"}`; a stale `expected` is refused).
- Added: `PUT /api/v1/projects/{slug}/deployments/{name}/feed`,
  `POST /api/v1/projects/{slug}/deployments/{name}/confirm-feed` and
  `POST /api/v1/deployments/confirm-feed`.
- Added: `POST /api/v1/projects/{slug}/deployments/{name}/start`, `/stop`
  and `/restart`.
- Added: `POST /api/v1/projects/{slug}/releases/{number}/approve` and
  `/cancel`, and `GET /api/v1/projects/{slug}/release-bundles`.
- Added: `GET /api/v1/project-creation-targets`; project drafts add
  `target`.
- Added: `GET /api/v1/projects/{slug}/model-profile`,
  `GET /api/v1/executor` and `GET /api/v1/steps/{id}/approvers`.
- Added: `POST /api/v1/account/tokens`,
  `DELETE /api/v1/account/tokens/{name}`, and
  `POST`/`DELETE /api/v1/groups/{name}/members/{user}`.
- Added: `PUT /api/v1/projects/{slug}/secrets/{deployment}/{name}/agent-visibility`
  and `POST /api/v1/projects/{slug}/secrets/{deployment}/{name}/separate-preview`;
  secret status adds `agentEligible` and `agentVisible`.
- `POST /api/v1/console/{sid}/upload` takes multipart form data with a
  `file` field instead of a JSON data URL.
- Areas that are switched off refuse their routes with an explanation
  naming the area.
- Deployments and deployment views add `feedRevision`, `feedConfirmed`,
  `approvalRole`, `promotedFromId`, `runtimeState`, `runtimeActor`,
  `runtimeAt` and `runtimeError`; views also add `status`,
  `servingRelease`, `runtimeControls` and the promotion fields
  `promotionSource`, `promotionRelease`, `promotionBundleId` and
  `promotionBlocked`. Deployment configuration requests add `from`.
- Releases add `approval`, `approvalRole`, `backupId`, `fromDeploymentId`,
  `rollbackOf`, `restoreBackupId`, `supersededBy`, `stage`,
  `stageEnteredAt`, `stageElapsedMs`, `lastStage`, `failedStage`,
  `interruptedByRestart` and `progressUncertain`. Release detail adds
  `decision`, `deploymentLabel`, `request`, `backup`, `backupReason` and
  `rollbackNumber`. Deploy requests add `releaseNumber`, `beforeRelease` and
  `expectedSourceBundleId`. The deploy stage adds `backing-up`.
- Backups add `runningReleaseId`, backup history adds `beforeRelease`, and
  the fleet backup list adds `deploymentRemoved`.
- Changes and change summaries add `chatRequest`, `requestSummary` and
  `requestGapQuote`; change pages add a required `checks` verdict and
  `notesDiff`; run snapshots add `checks`; steps add `isCheck` and
  `checkAttention`; change evidence adds `landingReleases`; check receipts
  add `agentEvidence`. `waitingOn.tone` can be `busy`.
- Activity adds `releaseApprovals`; activity deployments add `kind`,
  `status` and `projectStatus`; project rows add `status`.
- Usage by day adds `cached`. `GET /api/v1/authz/me` also reports deployment
  operate and deploy, and conformance review and fix permissions.
- Target capabilities drop `previews`. The `CheckReading` schema is renamed
  `checkReading` in the OpenAPI description.

## Deprecations

None.
