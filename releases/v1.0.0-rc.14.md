# Flokkit AppTown v1.0.0-rc.14

RC14 is about deciding and following a change. Change pages lead with the
decision: at most three actions, a checks shield beside the state, a short
explanation of a failed check with a recommendation, and a two-paragraph brief
of what the change does. What a change waits on is worked out once and said the
same way on Home, in lists, on the change page and in the CLI. While a change
runs, a Now block shows each step, and a landing draws the deployment through
named stages. Agents now run Pi 1.5.0 and model calls are priced from Pi's
model catalog. Built-in model providers offer only the models an operator has
enabled, landing runs every part's declared tests, and apps are given their
own address in `APPTOWN_APP_URL`. It includes all changes since RC13. Several
changes are breaking; read "Breaking changes" before upgrading. Take matching
database and file backups before upgrading, as described in the
[upgrade guide](https://github.com/flokkit/apptown/blob/main/stock/docs/guides/upgrading.md).

## Breaking changes

Models and agents:

- **Built-in model providers offer and admit only enabled models.** OpenAI,
  Anthropic and OpenRouter providers no longer offer every model in their
  catalog: an empty Enabled models list allows no models, including a stored
  default or model definition, and agent steps, chats and AppTown's own model
  calls that resolve to a model that is not enabled are refused. Saving a
  built-in provider's default requires it to be enabled, and a fuzzy `~`
  default is accepted only on custom endpoints with an empty enabled list.
  First-time setup enables the default it selects; nothing is migrated for
  existing providers. **Operator step:** on each built-in provider, open
  Model providers, choose Edit and enable every model your profiles and
  workflows use, including the provider's default, before agents next run.
  The provider page reads "Enable at least one model" until you do, and a
  profile choice outside the list is marked "not enabled on `<provider>`".
  Custom endpoints keep live discovery. Model-profile choices use the
  capability fields an endpoint reports; model names no longer decide them.
- **Agents run Pi 1.5.0** (was 0.84.3). Upgrading the worker brings the new
  agent image; existing sessions keep their format and resume. A model binding
  now admits only the API formats its provider serves: OpenRouter Chat
  Completions and Messages (Pi 1.5 sends OpenRouter's Claude models as
  Messages), OpenAI Responses, Anthropic Messages, and a custom endpoint's one
  configured format. A model entry naming any other format is refused before a
  call is made.
- **An agent or review step whose model never answered fails.** An attempt with
  no model output at all, for example because the provider refused every call
  with HTTP 429, was recorded as passed when a report or files from earlier
  rounds existed. It now ends as an error, "its model never answered", with the
  provider's last refusal when one was reported.
- **Spend recorded before this release has no price source** (migration 205).
  Amounts are unchanged. Usage, the change page and the CLI show "not priced"
  instead of $0, and "at least $X" when only some calls are priced.

Tests and landing:

- **Landing runs the test commands each part declares, and nothing else.**
  Automatic test-command detection and the tests step's `command` option are
  removed; a workflow that sets `command` no longer validates. Parts declare
  `test:` in `.apptown/app.yaml` (on `build` and `static` parts; refused on
  `image` parts), and every command runs in the part's folder. The stock
  landing workflow requires a declaration on every part built with Go, Node,
  Python, Ruby, Java, .NET or Rust, so **existing apps of those kinds fail
  their landing tests until a governed change adds `test:`**; this release
  does not add them. A test failing on the base branch no longer excuses the
  same failure on the change. Each command must work in a clean checkout,
  installing its own dependencies first (for example `npm ci && npm test`).
- **Every stock stage that boots the app checks guidance conformance before
  review,** and every failed check in a stage returns its full evidence to the
  agent for up to three automatic rounds. Later steps wait for earlier ones;
  review no longer runs after an unsuccessful boot, and an approval vote is
  refused until earlier steps have passed.

Apps and deployments:

- **AppTown gives every app its deployment's address in `APPTOWN_APP_URL`:**
  each part and init step on Docker and Portainer, App Platform services,
  workers and pre-deploy jobs, previews and data-protection rehearsals. It is
  unset while the address is not known, need containers do not get it, and an
  app may not set it in `environment`. `APPTOWN_URL` remains the AppTown
  server's address for the CLI and agent sessions. Domain previews restart
  once on their next use after the upgrade, because the address is now part of
  what they were booted with.
- **The WordPress starter takes its address from `WP_HOME`, then
  `APPTOWN_APP_URL`, then the validated request Host,** so WP-CLI gets the
  right address without a stored `WP_HOME`. A new WordPress pack version
  carries this guidance and adds a high-severity `deployment-home` check that
  judges the address from the page a visitor receives, plus a
  `wp-home-optional` rule; apps from the older starter fail it and can be sent
  remediation changes. **After such an app is fixed, remove any stored preview
  `WP_HOME` binding.** Adoption stays explicit.
- **Attached Docker hosts share one SSH connection per target.** AppTown writes
  an OpenSSH `ControlMaster` block for each attached host, with a private
  socket under its data folder, and runs up to three Docker calls at once per
  target. A data folder whose path makes the socket path too long, or an
  `ssh/c` folder that is not private, is refused with a message naming the fix.

HTTP API and CLI:

- **Change work moves from `GET /api/v1/dashboard` to `GET /api/v1/activity`.**
  The dashboard drops `pendingApprovals` and `activeRuns`; activity adds
  `waitingOnYou`, the changes the reader can act on now.
- **`waitingOn` is always an object.** Changes, change lists, runs and run
  detail carry `waitingOn` with `kind`, `run`, `step`, `checks`, `who`, `you`,
  `says` and `tone`. In CLI JSON, `apptown show` returns it in place of the
  former approval step or `null`, `apptown changes` rows add it, and
  `apptown wait --json` returns the holding step, so a script never approves a
  change whose check failed. Scripts that tested `waitingOn` for `null` must
  read `kind` instead.

## New and improved

- **Change pages lead with the decision.** The Overview shows the preview,
  request, result, checks and reviewer; Details keeps the full Work and Landing
  record. A decision offers at most three actions: move it on (Accept, Accept
  anyway, Continue, Try again or Re-check, as offered), Send back…, which
  opens its comment box in place of the buttons, and Abandon change. A checks
  shield beside the state is green when every blocking check passed, red
  naming what failed, amber when unknown and grey while running; advisory
  findings read "All checks passed · N notes".
- **A failed check is explained.** When a check fails and the change waits for
  a person, AppTown writes two or three plain sentences with the project's
  strongest model and recommends one of the acts it offers. It is advice: the
  check stays failed and the buttons do not change.
- **Approval briefs say what the change does,** in at most two short
  paragraphs written with the `main-strong` choice from the branch's patch,
  file list and the implementer's report or the chat. Without a model the
  decision screen shows the request.
- **What a change waits on is said the same way everywhere** ("review failed",
  "ready for your approval", "waiting for Reviewers", "chat open"). A held
  failed check wins over a later open approval. Home's "waiting on you" holds
  only changes the reader can act on now. Approvals name roles by their title.
- **A Now block shows what a running change is doing,** one line per step
  with its time, and stays open after Accept or Continue until the run
  finishes. Lists say the same ("Landing: deploying — step 1 of 2"), and a
  deployment with a release in progress reads "deploying · Release N".
- **A landing draws the deployment** through named stages (preparing,
  building, starting, checking, live), moving only when the deploy reports a
  stage. A landed change leads with "Release N is live", its address and Open
  the app. A failed deploy stops the drawing where it failed, records
  `failedStage` in its evidence, and says the app is not being served only
  when the running app had already been replaced.
- **Change starts in a chat.** Change on Home and the Projects list opens a
  chat change at once, with Catalog change and New change, detailed in its
  menu; a project with no chat model opens the detailed form. A chat change
  with no run offers Continue chat, and landing is done from the chat. The
  first message carries the request in the person's own words.
- **The chat page fits a phone.** Only the conversation scrolls, the composer
  sits on the keyboard and grows with the draft, and the head folds to one
  line once the chat has a message.
- **Direct OpenAI connections.** Model providers offers an OpenAI card using an
  `OPENAI_API_KEY` secret reference and the Responses API. Test connection
  fails on a refused key.
- **Model calls are priced from Pi's model catalog,** for agent and chat calls
  and AppTown's own calls, including cache reads and writes and tiered prices.
  OpenRouter's reported cost is used as before. Each spend line records where
  its price came from.
- **Provider refusals are said plainly:** "OpenAI refused the API key (HTTP
  401)", "refused access to `<model>` (HTTP 403)", "rate limit or out of
  credit (HTTP 429)", "had an internal error", "AppTown couldn't reach
  `<provider>`" or "`<model>` returned nothing".
- **AI checks read the part's source files.** A check may select
  `sourceFiles: true`: every programming-language file in the part's folder as
  identified by go-enry, skipping vendored, generated, documentation and binary
  files. Six stock checks use it; a Java app's checks now see its code. When
  the size budget cuts files the verdict says "judged on N of M matching
  files".
- **Node test counts.** The shipped Node guidance, toolchains guide and
  video-game starter make `node --test` write a JUnit report to
  `$APPTOWN_TEST_REPORT`; a readable report with zero tests says "no tests".
- **Conformance uses landing results.** After a change lands, its guidance
  check results are recorded against the landed commit (migration 204) and
  shown as the project's standing without running the checks again. An
  unconfirmed AI flag reads "needs review", not failed or unknown. Findings
  already covered by an open remediation change are left out of Fix counts and
  link to that change, and a request covering only such findings names the
  existing change instead of starting another.
- **Remediation explains its queue.** Queued items say why they wait and link
  to what blocks them; runs waiting for a person, a worker or between steps no
  longer hold their project. The job bar shows work under way with moving
  stripes.
- **Docker host readings.** Each attached Docker host has one background
  reader loop (migrations 202 and 203 remove the retired inventory jobs).
  Infrastructure shows each reading's age and how long it took. An unreachable
  host appears once in Attention, after two failed checks, with the number of
  deployments that cannot be checked. Docker commands return only after their
  connections close.
- **Attention is quieter.** A missed runtime reading waits two minutes before
  it is listed, working checks fold into one line grouped by kind, connections
  nobody set up are left out, and the four top-bar lights stay in place in grey
  when nothing is wrong. Backup protection and connection health are read
  hourly and after saves, backups and releases, and stay current for 75
  minutes. A bucket website has no backup to assess and raises nothing.
- **Deployments** is a list with a page per deployment, and readings refresh
  straight after a release. The capacity card shows its bars and says why a
  reading failed. The credentials page adds credentials inline at the top.
- **Clearer pages.** Inside a project the breadcrumb is the way up; project
  Activity leads a release with the change it shipped; the release page is one
  list of facts; Departures drop day headings; Open app shows unless the app
  was seen stopped.
- **Agents get better evidence.** Agent steps are told which declared needs
  started beside them; preview screenshots record failed stylesheet, script,
  image and font requests, and review agents receive the pictures. Large tool
  logs no longer hide the agent's answer, and a report saying "Blockers: none"
  no longer stops the change.
- **Fewer false findings.** npm checks run in the part's folder or in each
  top-level package below it; the toolchain check applies only to tools
  AppTown installs, not PHP; the README tone check no longer fails a plain
  fact the repository cannot prove. Pack updates carrying these fixes publish
  new versions; adoption stays explicit.
- **Local runs.** `apptown dev up` gives throwaway values for secrets AppTown
  generates and for declared defaults, and lists any it cannot supply. A failed
  init step reports its exit status and the last 1,500 characters of its
  output. Inside a workflow step, `apptown preview` explains how to check a
  boot. The trial script also warns when Docker has fewer than 4 CPUs or under
  30 GB of disk free.

## Declaration changes

App contracts add `test:` on `build` and `static` parts (see Breaking
changes). The workflow tests step drops its `command` option. Guidance check
declarations may add `sourceFiles: true`. No other application-contract,
workflow, check or pack declaration fields are added or removed.

## HTTP API changes

These changes are relative to RC13. The HTTP API remains experimental. The
[OpenAPI description](https://github.com/flokkit/apptown/blob/main/stock/docs/api/openapi.json)
contains the available route definitions.

- Added: `GET /api/v1/steps/{id}/advice` (a failed check's explanation, with
  `text` and `recommend`; needs `run:read`).
- `GET /api/v1/dashboard` drops `pendingApprovals` and `activeRuns`;
  `GET /api/v1/activity` adds `waitingOnYou`.
- Changes, change summaries, change detail, run rows and run detail add a
  required `waitingOn` object (`kind`, `run`, `step`, `checks`, `who`, `you`,
  `says`, `tone`; `who` lists deciders with `kind`, `name` and
  `displayName`). Run detail adds `pendingApproval`.
- Changes and change summaries add `abandonedBy`.
- Change usage adds `unpriced`; usage summaries add `providerReported`,
  `catalog` and `unpriced` counts of spend lines by price source.
- Project rows add `chatAvailable`.
- Deployments add `lastApplied` (`at` and `generation` of the last successful
  apply, or null).
- Infrastructure inventory readings add `tookSeconds`.
- Conformance responses add `openRemediations`, and check labels add
  `needs review`.

## Deprecations

None.
